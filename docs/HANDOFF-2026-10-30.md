## 2. Cel projektu i ogólne założenia

Projekt to rozwijany fork Fleasion rozszerzający obsługę cache Roblox, przeglądanie assetów, animacje, import zewnętrznych assetów i narzędzia do pracy z lokalną bazą.

Główne cele użytkownika:

- wygodnie przeglądać wpisy z Roblox cache / lokalnego DB;
- automatycznie rozpoznawać więcej typów assetów zamiast wrzucać je do `Other`;
- pokazywać rzeczywisty podgląd, a nie pustą tabelę lub sam hex, jeśli format jest rozpoznawalny;
- nie zacinać UI przy ciężkich wpisach;
- wyszukiwać i filtrować assety szybko;
- importować zewnętrzne assety i konwertować formaty do użytecznych formatów Roblox, w szczególności mesh;
- poprawnie obsługiwać assety zagnieżdżone w plikach RBXM, w tym animacje w folderach;
- zachować wygodę oryginalnego Fleasion / wcześniejszych narzędzi, ale bez duplikowania paneli i funkcji.

Przy projektowaniu zachowuj rozdzielenie ról:

- **Swaps** — operacje podmian / aktywne swapy.
- **Asset Explorer** — jedna główna lista cache assetów, filtry, wyszukiwanie, metadane i podgląd.
- **SQLite Browser** — bezpośrednia praca z tabelami, schematem i zapytaniami SQLite; to nie ma być drugi Asset Explorer.

### 3.5. Wykrywanie typów i obsługa payloadów cache

W `roblox_cache_store.py` dodano / rozszerzono obsługę:

- parsowania nagłówków HTTP z CRLFCRLF i LFLF, a także bloków znanych nagłówków bez pustego separatora;
- rozpoznawania nagłówków Roblox `roblox-assettypeid` (jeden rozpoznany nagłówek może wystarczyć do rozpoznania odpowiedzi);
- mapowania ID asset type na czytelne nazwy;
- wydobywania payloadu HTTP do podglądu, z pominięciem DCZ, którego nie da się poprawnie zdekompresować bez słownika;
- Zstandard: wrapper offset, kilka wariantów offsetu (obserwowane 8/10/12/16), konkatenowane ramki `read_across_frames=True`, strumieniowe wyciąganie z pliku;
- klasyfikacji m.in. DCZ, HLS `.m3u8` / type ID 86, HTTP response, JSON z ostrożnym rozpoznawaniem prefixu, CSGPHS;
- `is_roblox_compressed_payload`;
- `format_csgphs_preview` — na razie formatowanie metadanych nagłówka CSGPHS v8.

Nie wolno udawać pełnej dekompresji DCZ, kiedy wymaga on specyficznego słownika Zstandard Roblox, a słownika nie ma. W takim przypadku zachowaj surowe dane i pokaż metadane/dictionary SHA zamiast generować uszkodzony payload.

## 4.1. [P0] Sortowanie listy Asset Explorer — brakująca funkcja

Użytkownik wyraźnie chce klasyczne sortowanie 3-stanowe po kliknięciu nagłówka kolumny. Ma działać **dla wszystkich sortowalnych kolumn**, nie tylko Size lub Date. W szczególności: `Name`, `Kind`, `Size`, `Date` i pozostałe kolumny z danymi.

Wymagana sekwencja kliknięć na ten sam nagłówek:

1. **Pierwsze kliknięcie:** sortuj malejąco — np. Size od największego do najmniejszego, Date od najnowszego do najstarszego.
2. **Drugie kliknięcie:** sortuj rosnąco — np. Size od najmniejszego do największego, Date od najstarszego do najnowszego.
3. **Trzecie kliknięcie:** wyłącz sortowanie tej kolumny i przywróć dokładnie pierwotny/domowy porządek listy, taki jak przed kliknięciem nagłówka.

Następne kliknięcie po stanie neutralnym powinno ponownie rozpocząć od malejącego. Kliknięcie innej kolumny powinno zacząć jej cykl od malejącego.

Ważne wymagania implementacyjne:

- Stan sortowania musi być tri-state: `descending → ascending → none/original`.
- Stan neutralny ma przywracać **oryginalną kolejność źródłową**, a nie tylko przypadkowy sort po ID lub nazwie. Zachowaj stabilny `original_index`/kolejność scan resultów lub użyj właściwego modelu/proxy.
- Sortowanie Size ma korzystać z liczby bajtów, a nie tekstowego stringa typu `1.2 MB`.
- Sortowanie Date ma korzystać z timestamp/datetime, a nie sformatowanego tekstu daty.
- Name: sortowanie tekstowe bez wrażliwości na wielkość liter; rozważ natural sort, jeżeli nie destabilizuje wyników (np. `asset2` przed `asset10`).
- Kind: sortowanie po znormalizowanym rodzaju, nie po kolorze/ikonie.
- Puste / brakujące daty i rozmiary muszą mieć przewidywalne położenie w obu kierunkach.
- Dotyczy wszystkich nagłówków, dla których sortowanie ma sens. Jeśli kolumna jest akcją/ikoną, nie rób z niej sztucznej kolumny sortującej.
- Pokaż stan sortowania w nagłówku (strzałka w dół / w górę; brak strzałki w stanie neutralnym).
- Zachowaj zaznaczony asset po sortowaniu na podstawie stabilnego asset ID, a nie indeksu wiersza. Zachowaj preview, jeśli zaznaczony asset nadal istnieje i filtr go nie ukrył.
- Sortowanie nie może zmieniać kolejności danych w bazie ani zapisywać nowej kolejności do źródła cache.
- Po zmianie filtra/wyszukiwania zachowuj aktualny stan sortowania, ale po przejściu w neutralny stan powinna być odtworzona kolejność źródłowa aktualnego zestawu wyników.
- Nie przebudowuj kosztownie całej listy i nie dekompresuj payloadów w sort callbacku.

Testy wymagane:

- pierwszy klik Size = descending;
- drugi klik Size = ascending;
- trzeci klik Size = original order;
- ten sam cykl dla Date, Name i Kind;
- przełączenie na inną kolumnę rozpoczyna jej cykl od descending;
- sortowanie stabilne przy identycznych wartościach;
- wartości puste/None nie powodują crasha;
- zaznaczenie i podgląd nie przeskakują na inny asset po sortowaniu;
- filtrowanie + sortowanie nie gubi wpisów i neutralny sort wraca do pierwotnej kolejności.

Przed kodowaniem sprawdź, jaki widget/model jest aktualnie używany do tabeli w `src/fleasion/gui/roblox_cache_tab.py`. Nie zakładaj z góry, że to `QTableWidget` lub `QSortFilterProxyModel`.

- Używaj poziomu DEBUG tylko do szczegółów diagnostycznych; nie loguj na każdym kroku tysięcy wpisów przy zwykłym skanie.

## 10.3. JSON-y z zakodowaną zawartością

Użytkownik zauważył, że **niektóre pliki rozpoznawane jako JSON są zakodowane**. Obecny `json.loads()` na surowym body nie wystarczy.

Do zbadania i naprawienia:

## 10.11. Logi — dodatkowe, konkretniejsze wymagania

Poprzednia sekcja 4.2 opisywała ogólny trwały system. Użytkownik doprecyzował teraz: **logi Fleasion są zbyt duże, bo logowane jest praktycznie wszystko. Nie loguj każdego cache ani zwykłego wpisu.** Potrzebne są problemy i istotne zdarzenia, nie pełna kopia ruchu.

### 12.2 Kompatybilność ze starymi konfiguracjami oryginalnego Fleasion

Użytkownik chce móc wziąć stare pliki konfiguracyjne z oryginalnego Fleasion i zaimportować je do forka bez ręcznego odtwarzania swapów. Jest to osobny, ważny zakres funkcjonalny, a nie tylko eksport/import nowego formatu.

Problem techniczny: oryginalny Fleasion może opisywać cache/asset przez **Roblox Asset ID**, natomiast nowy backend `Fleasion-db` opiera część odwołań na **hashach zawartości**. Samo przepisanie liczby ID na hash nie jest możliwe bez poznania zawartości assetu. Potrzebny jest adapter migracyjny, który rozwiązuje oba formaty i pobiera brakujące dane.

Wymagany docelowy workflow:

1. Użytkownik wybiera `Import`/`Load` starego configu Fleasion (pojedynczy plik lub cały zestaw, zależnie od rzeczywistego formatu upstreamu).
2. Program wykrywa format i wersję starego configu oraz odczytuje reguły swapów, profile, nazwy, aktywność, grupy i ścieżki plików.
3. Dla każdego starego Asset ID sprawdza lokalne indeksy/cache i mapowania `asset_id + asset_type (+ wersja/źródło)` → hash.
4. Gdy mapowanie istnieje, wykorzystuje istniejący hash i nie pobiera ponownie assetu.
5. Gdy mapowania brakuje, program próbuje pobrać oryginalny asset z właściwego źródła (z użyciem istniejącego mechanizmu pobierania/autoryzacji, jeśli jest wymagany), weryfikuje odpowiedź, zapisuje bajty do własnego magazynu i oblicza hash dokładnie tym samym algorytmem, którego używa backend.
6. Program tworzy trwałe mapowanie starego ID do nowego hasha i zachowuje informację źródłową, np. oryginalny Asset ID, typ, źródło, datę pobrania oraz wynik weryfikacji.
7. Następnie migruje swap do wewnętrznego formatu nowej aplikacji, aby działanie nie zależało od dostępności starego configu ani od ponownego pobierania tych samych plików.
8. Jeżeli nie da się pobrać assetu (brak uprawnień, usunięty asset, błąd sieci, brak typu lub niejednoznaczność), nie wolno tworzyć fikcyjnego hasha ani cicho pomijać wpisu. Pokaż raport importu z pozycją `unresolved/missing`, źródłowym ID, przyczyną i sposobem ręcznego wskazania pliku.
9. Po udanym imporcie użytkownik ma widzieć normalne, aktywne reguły w Replacerze i móc je edytować, grupować, włączać/wyłączać oraz przełączać profile jak w oryginale.

**Istotne:** mapowanie musi znać rolę ID w regule. Jeżeli konfiguracja wskazuje oryginalny asset, który ma zostać przechwycony/zamieniony, oraz osobny asset lub plik używany jako zamiennik, migracja musi rozwiązać obie strony niezależnie. Nie wolno zakładać, że każdy ID w JSON oznacza tę samą stronę swapa.

### 12.3 Nie modyfikować oryginalnych konfiguracji Fleasion

Kompatybilność nie może być realizowana przez otwieranie i zapisywanie starych plików „w miejscu”. Użytkownik wyraźnie chce zachować oryginalną instalację i jej konfiguracje bez zmian.

- Nowy fork ma mieć własny, odrębny katalog danych konfiguracyjnych i assetów, z odrębną nazwą aplikacji/katalogu.
- Nie zapisywać nowych ustawień, profili, migracji, cache, hash-indexów, importowanych plików ani logów w katalogu oryginalnego Fleasion.
- Odczyt starego katalogu może być dozwolony jako źródło migracji, ale ma być tylko do odczytu. Nie wykonywać automatycznej migracji „w miejscu”.
- Podczas importu kopiować/konwertować dane do nowej przestrzeni. Stary plik pozostaje identyczny bajt w bajt.
- Domyślnie zapisywać wszystkie późniejsze zmiany tylko w nowym katalogu. Eksport zgodny ze starym formatem może być osobną, jawnie wybraną operacją `Export`, która tworzy nowy plik w ścieżce wskazanej przez użytkownika; nie nadpisywać źródła bez osobnego potwierdzenia.
- W czasie pierwszego uruchomienia nie należy samoczynnie przepisywać oryginalnych plików ani zmieniać ich ustawień.

Przykładowy rozdział katalogów do sprawdzenia i dopasowania do istniejącej architektury platformowej (to propozycja, nie założenie o obecnym kodzie):

- Windows: osobny katalog aplikacji pod `%APPDATA%`/`%LOCALAPPDATA%`, np. `Fleasion-db` lub `Fleasion Extended`, różny od katalogu oryginalnego `Fleasion`.
- Linux: osobny `~/.config/<nazwa-forka>` oraz osobny katalog danych/cache pod `~/.local/share/<nazwa-forka>`.
- macOS: osobne `~/Library/Application Support/<nazwa-forka>` oraz właściwy katalog preferences.

Nazwa katalogu powinna być jedna, stabilna i używana konsekwentnie przez config, profile, asset store, cache, logi i backupy. Najpierw sprawdzić obecne `CONFIG_DIR`, `CACHE_DIR`, `LOGS_DIR`, `APP_NAME` oraz migracje ścieżek w branchu. Nie zmieniać ich w ciemno, bo może to spowodować utratę dostępu do aktualnych danych użytkownika. Dodać migrację danych **z obecnego forkowego katalogu do nowego forkowego katalogu**, jeżeli zmiana nazwy tego katalogu jest konieczna; nie łączyć jej z oryginalnym Fleasion.
### 12.4 Format nowej konfiguracji i przenośność

Nowy format powinien być wersjonowany i samowystarczalny:

- `schema_version` / wersja formatu;
- unikalny identyfikator profilu i nazwa profilu;
- lista swapów z czytelnym `source` i `replacement`;
- referencje do plików przez ścieżki względne, a nie absolutne ścieżki autora;
- informacja o oryginalnym Roblox Asset ID i typie, jeżeli istnieje;
- wewnętrzny hash zawartości, jeżeli plik został już pobrany i zapisany;
- metadane pobrania/źródła oraz stan walidacji;
- stany enabled/disabled, kolejność, grupy i inne ustawienia potrzebne do zachowania zachowania oryginalnego Replacera.

Konfigurację trzeba móc eksportować jako bundle zawierający manifest oraz wymagane pliki lokalne. Po imporcie na innym komputerze program ma wykryć brakujące pliki, rozpakować/umieścić dostępne pliki w prywatnym asset store i odtworzyć mapowania hashy. Nie używać absolutnych ścieżek, które działają wyłącznie na komputerze osoby tworzącej konfigurację.

Hash powinien być identyfikatorem zawartości, ale nie zastępuje źródłowego Asset ID. Oba identyfikatory należy zachować, gdy są dostępne: Asset ID służy do rozpoznawania/pobrania oryginalnego zasobu i kompatybilności z dawnym configiem, hash służy do lokalnego, stabilnego odwołania do konkretnych bajtów. Jeżeli zawartość assetu zmieni się pod tym samym ID, nie nadpisywać bez sprawdzenia starej wersji — zachować odrębne wersje/hash i raportować konflikt.

### 12.5 Testy akceptacyjne migracji

- Import poprawnego, starego configu Fleasion tworzy profile i swapy w forku, a oryginalny plik nie zmienia SHA-256 ani czasu modyfikacji.
- Import tego samego configu drugi raz nie duplikuje niepotrzebnie assetów ani profili; program ma zaproponować aktualizację/ponowne załadowanie lub wykryć duplikat.
- Asset ID obecny w lokalnym cache zostaje przemapowany bez pobierania sieciowego.
- Brakujący asset jest pobierany, hashowany i mapowany; późniejszy import używa istniejącego lokalnego hash.
- Błąd pobierania/nieautoryzowany/nieistniejący asset daje jasny raport i nie tworzy uszkodzonej reguły.
- Jeśli źródłowy config ma wiele profili, wszystkie profile, grupy, kolejność i aktywność zostają zachowane.
- Bundle wyeksportowany z komputera A można zaimportować na komputerze B bez zachowania absolutnych ścieżek z komputera A.
- Zapis, przełączenie profilu i zamknięcie aplikacji zmieniają tylko pliki w nowym katalogu forka; oryginalne Fleasion nadal uruchamia się z niezmienionymi konfiguracjami.
- Jawny eksport do starego formatu zapisuje nowy plik w wybranym miejscu i nie nadpisuje źródła po cichu.

## 13. Dopisek do promptu startowego następnego chatu — obowiązkowy

**Odtwórz GUI oryginalnego Fleasion tak samo, a nie tylko podobnie.** Zachowaj dokładne nazwy i miejsce elementów. `Local DB` musi pozostać widoczne pod nazwą `Local DB`; nie usuwaj ani nie przemianowuj jej na `Swaps`. `Scraper DB` również zachowuje oryginalną nazwę i GUI, ale jego stary, niedziałający scraper ma zostać zastąpiony nową, działającą implementacją. Nie trzeba zachowywać starych klas, API ani pipeline'u — nowy backend może być całkowicie inny. `Replacer` zachowaj w takim miejscu i pod taką nazwą, w jakiej występuje w upstream; najpierw ustal, czy jest oddzielny od Local DB, nie zgaduj. Użytkownik chce kompatybilności ze starymi plikami konfiguracji oryginalnego Fleasion: stare reguły mogą wskazywać Roblox Asset ID, podczas gdy nowy backend identyfikuje lokalną zawartość hashami. Zaimplementuj osobny adapter importu/migracji: odczytaj oryginalne configi, rozwiąż ID przez obecny indeks/cache, a gdy trzeba pobierz asset, zweryfikuj go, oblicz hash i utwórz mapowanie ID→hash. Rozwiąż niezależnie obie strony każdego swapa. Nierozwiązywalne ID pokaż jako problem do naprawy — nigdy nie zgaduj hasha. Zachowaj ID jako metadane i hash jako lokalny identyfikator bajtów.

**Bezwzględnie nie zapisuj do oryginalnego katalogu Fleasion.** Stare configi są wejściem tylko do odczytu. Utwórz osobną, stabilną przestrzeń danych forka dla configów, profili, importowanych assetów, hash-indexu, cache i logów. Migracja ma kopiować/konwertować do tej prywatnej przestrzeni; oryginał ma pozostać niezmieniony. Sprawdź istniejące ścieżki w branchu przed zmianami i przygotuj bezpieczną migrację obecnych forkowych danych, jeśli zmiana katalogu jest konieczna. Nowe profile i bundle eksportuj z plikami przez ścieżki względne, by działały na innym komputerze. Zanim uznasz kompatybilność za gotową, dodaj testy SHA-256 oryginalnych configów przed/po migracji oraz test importu, ponownego importu, brakujących assetów i kilku profili.
